The small-model pipeline

One engine for compile, research, and rails · spec · 2026-07-31 · canonical source: 2026-07-31-small-model-pipeline-design.md

The harness already knows the trick that makes small local models useful: invert control — the harness decides what happens, the model fills one narrow, schema-locked slot per call. Rails proved it for drills; the weak-compile fallback re-implemented it by hand. This spec extracts the trick into one engine with three consumers: a rebuilt compile, a new background research drain, and (last, once proven) rails generation itself.

The governing rule, enforced not prompted: this system conveys sourced human knowledge — it does not generate knowledge. Machine-written pages carry mechanically-verified sources or stay draft forever.

1The engine src/server/pipeline.ts

  • Fit check first — token math (chars/4 floor) against the model's known context. Too big → split; never send a prompt that will be silently truncated.
  • Recursive split — bisect on natural boundaries (headings → paragraphs → hard length) until every piece fits one call.
  • Parallel map — pieces run concurrently (default 4, per-role knob).
  • One call per piece — structured generation, constrained decoding, exactly one rejection-retry (the rails recipe).
  • Vote for hard steps — a step marked vote: n runs n calls, majority wins. Off by default; synthesis and ranking opt in.
  • Diagnosed failure, never mystery — every failure classified before any fallback: overflow (fit math) · weak-output (schema rejected after retry) · transport (endpoint down — re-throws so queues retry). The class rides the ledger receipt.
  • Merge step — consumer-supplied reducer (writes the MOC, joins extracts), same fit/retry machinery.
  • Floor — consumer-supplied deterministic fallback per piece, always labeled with the diagnosed reason. Model weakness never surfaces as a learner-facing error.
runPipeline({ role, steps, concurrency }, job) -> { results, receipts }
// step: { name, prompt(piece), schema, vote?, floor?(piece, reason) }

Interface shape is a plan-level decision; this is the contract sketch.

2Compile, rebuilt on it

Chapter → fit check → recursive split → parallel distillation (one page per part, 150–400 words, faithful to the text) → MOC merge: one hub page per chapter — the Obsidian map-of-content idiom — one line per part, prereqs/deepens edges to every part page. Parts stay individually drillable with their own mastery.

  • Citation wrapping stays mechanical: every part page carries its book/chapter source.
  • Verbatim floor survives, but only after diagnosis: part 3: verbatim (weak-output: schema rejected twice) — never just "fallback".
  • The agentic compile path (strong models driving write_page) is untouched.

3The research drain background-first, compile-drain-shaped

Triggers: a planner-picked vaultGap page (stub / unsourced / thin) · a cold-topic ask · an explicit request. Drills never wait.

  1. model writes 2–3 search queries from the topic + what the vault has
  2. harness hits SearXNG (search.searxng required — absent → the drain refuses loudly at enqueue, it does not pretend)
  3. model ranks result snippets (classification; vote)
  4. harness fetches top pages (existing read_url machinery)
  5. model extracts relevant passages, parallel per page
  6. model writes page(s) from those passages only, inline citations; multiple concepts → part pages + MOC, same shape as compile
  7. harness mechanical citation check — every cited quote must appear verbatim (whitespace-normalized) in its fetched source. Failing claims are cut. A page that loses all citations is not written; the receipt says why
  8. harness writes pages as draft with sources: = verified URLs, via Engram (single-writer rule)

Dead ends degrade loudly: no results, failed fetches, or all citations cut → a receipt saying exactly that. Nothing is invented to fill the gap — that is the point.

4The enforcement rule

  • Pages written by compile or research always carry sources (the book, or the verified URLs) — mechanically.
  • A page with no sources can never be promoted past draft by machinery. The rule binds the harness, not the learner.
  • vaultGap already treats unsourced as a gap; the research drain finally closes that loop for local-model setups.

5UX parity

  • Chip-style status while the drain works a visible request: "searching…", "reading <domain>…", "writing <page>…"
  • Receipts in the library exactly like compile receipts; the progress card counts new pages.
  • A cold-topic ask stages its first drill the moment the first page lands.
  • The visible difference from a frontier model is wall-clock only — background-first hides most of it.

6Config

  • New model role research (defaults to the compile model) — prefix routing, sampler blocks, usage ledger all apply.
  • search.searxng is the retrieval backend, unchanged.
  • Per-role concurrency, default 4.

7Testing

  • Engine: pure offline unit tests — fit math, split boundaries, parallel map, vote, failure classes, merge, floor labels.
  • Compile: existing ingest tests carry over; new ones pin the MOC and the diagnosed-reason ledger text; the CI weak-model server drives the whole ladder (reject-rf included).
  • Research: fake SearXNG + fake fetch pin ranking, extraction, the citation check (a fabricated quote is cut; a page losing all citations is not written), dead-end receipts. One e2e: trigger → receipt → page + MOC in the library.
  • Rails migration: only after everything above is green; rails' e2e must not change at all — byte-identical behavior is the acceptance test.

·Build order

  1. Engine + unit tests
  2. Compile refit (offline, weak-model CI)
  3. Research drain + UX receipts
  4. Rails migrates; all specs stay green
