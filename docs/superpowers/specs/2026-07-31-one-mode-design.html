One mode

Collapsing the mode selector — design, 31 Jul 2026

1. What the four modes actually are

Read from prompt.ts and session.ts, not from memory:

ModeWhat it changesEnforced by
learn“Teach the next suggested lesson.”nothing — one sentence
review“Re-prove decayed/due pages before anything new.”nothing — one sentence
quiz“Open with a quiz block covering recent pages.”nothing — one sentence
freeformadds ingest + create_path; always agentic (never rails)real code
The finding

Three of the four modes are a framing sentence. No tool gate, no code path, nothing enforced. Everything they nominally control the harness already computes independently: next_lessons picks the frontier, decay picks what is due, and the session plan already interleaves [review] / [new] / [fix] items in a deliberate order.

Only freeform is real — and it is not a learning mode. It is a permission level: may this turn restructure the vault?

2. The codebase already routes around the selector

Three separate mechanisms exist for no other purpose. This is the system’s own evidence that the control is in the wrong place.

coldStartMode.ts

Auto-picks freeform when the vault has no real pages, because learn could not write and “the newcomer’s first lesson researched well, taught well, and then evaporated.”

writeIntent.ts + writeUp

A one-shot promotion of a single turn to freeform, existing verbatim so the learner does not have to “hunt for the mode selector and flip to freeform by hand.” The visible mode never changes; the next turn reverts.

Mode slash commands

/review, /freeform override the selector for one turn — a second way to say the same thing, because the persistent selector is the wrong granularity.

And as of today

write_page now unlocks in teaching modes whenever a vault gap opened research. The freeform boundary is already mostly gone; what is left of it is ingest and create_path.

3. Proposal

Remove the mode selector. Keep Mode internally as a derived value.

That second half is the point. Deleting the concept would touch the plan builder, rails, the prompt, the slash commands and a large number of tests. Deriving it instead is a small change with the same user-visible result, and it leaves every internal seam intact.

TodayReplaced by
User picks learn/review/quizThe session plan. It already computes review-due, frontier and fix items, and rule 2a already says execute it in order.
User picks quiz“quiz me” as a sentence, plus the existing /quiz command.
User picks freeform to write a pageAlready automatic — vaultGap unlocks write_page.
User picks freeform to build a syllabus / add materialAn explicit intent affordance — see 4.

4. The one real decision: authoring

ingest and create_path are the only capabilities with no automatic trigger. Two options.

A. Auto-unlock on intentrecommended

Unlock them when the turn’s text asks for them — “build me a path for X”, “add this material”. Same shape as vaultGap: a per-turn unlock, decided by the harness, announced to the model in the tail note.

Why: consistent with everything else here, and with rule 1b — the system should not ask the user to answer a question it can answer itself. Risk: a model authoring a path nobody asked for. Mitigated by the same thing that mitigates it today — create_path is visible, reversible, and the tutor must say what it built.

B. Keep an explicit affordance

No auto-unlock; a button (“build me a syllabus”) arms one turn, exactly like the existing writeUp latch.

Why: zero risk of unasked-for authoring, and reuses a proven mechanism. Cost: a learner who says “build me a path for music theory” in words gets told to press a button instead — the failure this whole redesign is meant to remove.

5. Risks, named

Rails

Rails currently gates on mode !== 'freeform'. If freeform stops being a persistent mode, that gate needs a new definition. Proposed: rails drives plan execution; any turn that unlocks writing, ingest or path-building goes agentic. That is what the current gate means in practice, stated in terms of capability rather than mode.

Losing manual control

Some sessions genuinely want forcing. The slash commands stay — /review, /quiz, /freeform — as per-turn overrides. What goes is the persistent selector, not the ability to say what you want.

The plan must carry more weight

The honest cost. Today the framing sentence does quiet steering (“open with a quiz”). Removing it means that steering has to move into the plan builder, which currently emits [review]/[new]/[fix] but never “this page is ripe for a quiz”. This is the actual work of the change; the deletion is trivial by comparison.

6. Migration

  1. Add deriveMode(plan, text, vault) — one pure function, unit-testable, returning today’s Mode. Ship it behind the existing selector, asserting it agrees.
  2. Teach the plan builder to mark quiz-ripe items, so quiz’s steering survives its framing sentence.
  3. Restate the rails gate in capability terms.
  4. Add the authoring unlock (option A).
  5. Remove the selector from the topbar. Keep the slash commands.
  6. Delete coldStartMode — with writing auto-unlocked it has nothing left to decide.

7. What I would not do

  • Delete the Mode type. It is a fine internal representation; the bug is asking a human to set it.
  • Collapse to one mode and stop. Without step 2 the quiz steering is silently lost and nobody notices for weeks.
  • Remove the slash commands. They are the escape hatch that makes removing the selector safe.
